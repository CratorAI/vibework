# Releasing (owner-run only)

No release workflow has been run as part of preparation. Resolve licence,
Claude SDK redistribution/login terms, trademark provenance and dependency
notice inventory before publishing. Test on clean Apple silicon and Intel Macs.

## One-time setup

Choose whose Apple Developer Program membership and Developer ID Application
certificate will sign the app. In Apple Developer, create that certificate using
a certificate signing request from Keychain Access; import the issued certificate
and export the identity plus private key as a password-protected `.p12`. Keep
backups private. Do not commit any certificate or key.

Create these GitHub Actions repository secrets:

| Secret | Owner supplies |
| --- | --- |
| APPLE_CERTIFICATE | Base64 encoding of the exported `.p12` |
| APPLE_CERTIFICATE_PASSWORD | Export password |
| APPLE_SIGNING_IDENTITY | Full Developer ID Application identity name |
| APPLE_TEAM_ID | Membership team ID from Apple Developer |
| APPLE_ID | Apple account used for notarization |
| APPLE_PASSWORD | App-specific password created at account.apple.com |
| TAURI_SIGNING_PRIVATE_KEY | Contents of Tauri's generated private key file |
| TAURI_SIGNING_PRIVATE_KEY_PASSWORD | Password chosen for that key (define even if empty) |

This workflow uses Apple ID notarization, not App Store Connect API keys. An API
key alternative would require changing the script to use APPLE_API_KEY,
APPLE_API_ISSUER and APPLE_API_KEY_PATH, and securely materializing the `.p8`.
No such key or certificate is generated by this repository.

Generate the updater key pair yourself, outside the checkout:

```sh
bunx tauri signer generate -w "$HOME/.vibework-updater.key"
```

Keep the private key and password backed up; losing it prevents existing users
from trusting future updates. Replace `REPLACE_WITH_TAURI_UPDATER_PUBLIC_KEY` in
`src-tauri/tauri.conf.json` with the generated public key text. Public keys are
intentionally public; never paste the private key there. The endpoint in the
same config is the public repository's latest Release `latest.json`. Change it
if publishing to a different repo. No runtime environment override is supported.

For a local signed build, use an already imported Developer ID identity and
supply the same environment variables from your own secure credential tooling.
Keychain item names are your choice: no named credential or identity is assumed
by the repository. `bash scripts/release-macos.sh` builds but does not publish.

## When someone else holds the Developer ID

If another person signs on the project's behalf, they do not need the source.
Build an unsigned app here (`bash scripts/install-app.sh --build-only`), then
send them a folder with `Vibework.app`, `src-tauri/Entitlements.plist` and
`scripts/sign-kit/sign.sh`. They run `sign.sh` with their own identity and
notarization profile (instructions are at the top of the script) and send
back the signed DMG and the zipped, stapled app. Their certificate and
password never leave their Mac. Make the updater bundle from the returned app
with `bunx tauri signer sign`, then publish.

## Each version

1. Change **package.json version only**, run `node scripts/version.mjs`, commit
   the synchronized Cargo manifest and lockfile. Tauri reads package.json directly.
2. Write optional `RELEASE_NOTES.md`, run README checks and
   `RUSTFLAGS='-D warnings' cargo build --manifest-path src-tauri/Cargo.toml`.
3. Verify the release build has no dev bridge. Never pass `--features dev-release-probe`.
4. After owner approval, push a `v<version>` tag. The workflow verifies the tag,
   builds both native macOS targets, signs, notarizes and staples the app and DMG,
   produces signed updater bundles and publishes their manifest and release assets.
5. Download and test both DMGs, signature validation, launch, an idle update,
   an update deferred by a running task and a failed-signature update. Verify
   `latest.json` only refers to successfully uploaded architecture assets.

Apple silicon and Intel sidecar checksums are pinned. Intel execution and the
GitHub runner matrix have not been tested locally. The workflow has no manual
trigger and branch pushes do not run it. The updater automatically checks at
most daily on launch, downloads in the background and installs on quit or an
explicit restart when tasks are idle. A placeholder key reports not configured.
